# Contributing

Thanks for wanting to contribute.
One rule up front:

**Human-authored pull requests targeting `main` must be raised through [`no-mistakes`](https://github.com/kunchenguid/no-mistakes).**
We require this to reduce the maintainer's burden of reviewing and merging contributions.

`no-mistakes` puts a local git proxy in front of your real remote.
Pushing through it runs an AI-driven review/test/lint pipeline in an isolated worktree, forwards the push upstream only after every check passes, and opens a clean PR automatically.

A GitHub Actions check (`Require no-mistakes`) runs on PRs targeting `main` and fails if the body is missing the deterministic signature and pipeline attestation that no-mistakes writes.
The attestation must describe the PR's current head and record the review, test, and document steps as completed.
The release and dependency bots are exempt so their automation keeps working, but regular contributor PRs without the signature will not be reviewed or merged.

## Workflow

1. Fork the repo, then clone the parent repo or set your local `origin` back to the parent repo (`git@github.com:kunchenguid/gh-axi.git`).
2. Create a branch and make your changes.
3. Initialize or refresh the gate with your fork as the push target: `no-mistakes init --fork-url git@github.com:<you>/gh-axi.git`.
4. Commit your changes.
5. Push through the gate instead of pushing to `origin`:

   ```sh
   git push no-mistakes
   ```

6. Run `no-mistakes` to attach to the pipeline, watch findings, and auto-fix or review as needed.
7. Once the pipeline passes, it pushes the branch to your fork and opens the PR against this repo for you.

The required pipeline attestation and fork routing require no-mistakes **v1.46.0** or newer.
Run `no-mistakes update` before `git push no-mistakes` if your installed version is older.

See the [no-mistakes quick start](https://kunchenguid.github.io/no-mistakes/start-here/quick-start/) for the full first-run walkthrough.

## Repo conventions

- Node 20+, TypeScript, ESM-only.
- Install dependencies with `pnpm install --frozen-lockfile`; run `pnpm run build` and `pnpm test` before pushing.
- After changing dependencies, run `pnpm exec prettier --write pnpm-lock.yaml` so the committed lockfile keeps its Prettier formatting.
  The committed lockfile uses multi-line `resolution:` and `engines:` blocks, which is not pnpm's native output. A plain `pnpm install` rewrites those blocks inline and produces about a thousand lines of cosmetic churn. CI runs `pnpm install --frozen-lockfile`, which accepts the Prettier-formatted file.
- Do not hand-edit `CHANGELOG.md` or `.release-please-manifest.json`.
  They are regenerated by release-please from your conventional commit messages.
- Do not bump `package.json`'s `version` by hand for ordinary changes.
  release-please updates it in the release PR.
- Do not hand-edit `skills/gh-axi/SKILL.md`.
  It is generated from `src/skill.ts`, including frontmatter metadata; run `pnpm run build:skill` and commit the result.

## Release and gate maintenance

Release-please cuts releases from conventional commits on `main`. Merging its release PR publishes to npm through `.github/workflows/release-please.yml`.

Every `pull_request` workflow (`ci.yml`, `guard-generated-files.yml`, `no-mistakes-required.yml`) `paths-ignore`s the release-please output set (`.release-please-manifest.json`, `CHANGELOG.md`, `package.json`) so a release PR creates zero runs. Job-level bot exemptions stay as defense in depth. `test/release-ci-exclusions.test.ts` derives that set from `release-please-config.json` and fails if a workflow drifts. Update the ignore lists when adding `extra-files` or changing `release-type`.

`.github/workflows/no-mistakes-required.yml` calls the shared `kunchenguid/no-mistakes` `require-no-mistakes` action at an immutable commit SHA, never `@main`. Enforcement (the `Updates from [git push no-mistakes]` signature, the `<!-- no-mistakes-pipeline-attestation:v1 {...} -->` comment, and head binding) and its tests live in the no-mistakes repository. Change them there, then bump this repo's pin in a separate pull request. This repository owns the workflow's `on:`, `paths-ignore`, `concurrency`, `permissions`, job name, and author-exemption `if:`. A body whose attestation was not rewritten for the current head fails the check. Push through `git push no-mistakes` so the body is refreshed.

## Implementation invariants

`gh.ts` appends `--repo` for any repo context whose source is not `git`. `gist` and `project` are user-scoped or owner-scoped and reject that flag, so their handlers must not pass a `RepoContext` into `ghJson`. `project` may still read `ctx.owner` to default `--owner` to the current repo owner, then `@me` when no repo context exists. `gh project` uses `--format json`. List responses are wrapped objects, and item/field rendering flattens unknown scalar fields into columns. A missing `project` or `read:project` scope is mapped to `FORBIDDEN` with a `gh auth refresh -s <scope>` suggestion. That scope mapping is generic, not project-specific.

Every entry in a family's `*_FLAGS` table must appear in the matching `flags{<sub>}:` section of its `*_HELP` string. `test/help-examples.test.ts` checks that direction. Matching is whole-token. `issue list --search` and `pr list --search` are the only `UNDOCUMENTED_ON_PURPOSE` exemptions, because those flags always fail and point at `gh-axi search`. Add an exemption only for a flag that always fails. `api`, `gist`, `secret`, and `stack` declare flags differently and are not covered. When a flag becomes repeatable, mark it `(repeatable)` in that help string.

`gh` accepts `--label`, `--assignee`, `--reviewer`, `--project`, and the `--add-*` / `--remove-*` variants once per value. Collect every occurrence with `getAllFlags` or `takeAllFlags` plus `pushRepeated`. `getFlag` and `takeFlag` keep only the first value. Both collectors reject a dangling or blank value. `issue.ts` reads args with `getAllFlags`. `pr.ts` consumes them with `takeAllFlags`.

`pr merge` rejects conflicting method switches (`--merge` / `--squash` / `--rebase`) and conflicting auto switches (`--auto` / `--disable-auto` / `--admin`) locally, before any `gh` call. Verify a new conflict against the installed `gh` rather than inferring it from help text. `takeBoolFlag` rejects a boolean written as `--flag=value` with a VALIDATION_ERROR. Commands that also take string values consume those value flags first, so a value like `--desc --secret=true` is not misrejected (see `createGist`). A bare declared flag in a value position is a missing-value error, never a value — value consumers take the command's declared flags as a protected list, and a dash-leading value stays available via the `--flag=value` form. `prMerge` rejects valued boolean merge switches on the raw argv with `rejectValuedMergeSwitches`. `--match-head-commit` parsing is specified in `src/cli.ts` `parseRepoContextArgs` and `src/commands/pr.ts` `prMerge`.

`mapGhError` in `src/errors.ts` returns on the first matching pattern. A narrower pattern must sit ahead of any broader one that would swallow it. When gh embeds a generic remediation hint in a different root cause, match the specific carrier first. `test/errors.test.ts` pins repo-resolution and genuine-auth cases.

`gh-axi stack` is a strict adapter over `github/gh-stack`, not a second stack engine. Commands are cwd-bound: `withLocalRepoContext` rejects explicit repo flags and `GH_REPO`, strips `--hostname`, and does not pass a `RepoContext` through, because the extension rejects `--repo`. Preserve both stdout and stderr and the exact `StackError` exit code, including actionable exits 2-10. Do not replace `ghRaw` with `ghExec` or `mapGhError`. Force `view --json`, `submit --auto`, and `merge --yes`. Require arguments for commands that would otherwise prompt. Leave `modify`, `switch`, `alias`, and `feedback` out unless upstream gains a headless interface.

`--attach` is repeatable on issue and pull request `create`, `edit`, and `comment`. gh-axi checks that `GH_BIN` or `gh` on `PATH` is at least 2.99.0, then forwards the values unchanged. Tests resolve that binary from `GH_BIN`, then a worktree `.tools/gh-2.99.0/**/bin/gh`, then `PATH`. Live upload tests need `GH_AXI_TEST_REPO` set to a captain-owned test repo, never a product repo.
